# 海上风电机组维检 Agent 开发

## 开放性说明

本题是一道开放性设计与开发题，不存在唯一正确的技术方案。候选人可以根据自己的经验、时间安排和能力范围选择实现方式及完成范围。

题目提供的问题用于展示预期应用场景和不同难度层次，不要求候选人的系统必须完整解决所有问题。

我们会综合考察候选人的问题分析、方案设计、核心功能完成度、代码组织、UI 产品设计、AI 工具使用方式，以及对当前实现和局限性的理解。

一个范围合理、核心流程清晰、能够稳定解决部分问题，并且候选人可以清楚解释其设计与取舍的系统，同样可以进入二面。

请优先完成你认为最能体现自身能力的部分，不建议为了覆盖全部问题而堆叠大量未经验证的功能。

本题不考察海上风电行业背景。回答问题所需的业务知识均包含在随题数据库和文档中；不要求使用特定 Agent 框架，不要求采用多 Agent，不要求实现生产级系统，不要求所有问题全部通过，也不要求答案与参考答案逐字一致。我们不评价复杂视觉效果，重点关注系统是否具备合理的数据查询、文档检索、信息融合和依据展示能力。

## 一、题目背景

某虚构海上风电场保存了风机运行告警和维检工单数据，同时拥有故障处理手册和检修作业管理规程。请自行设计并实现一个“海上风电机组维检 Agent”，使用户可以用自然语言询问风机状态、告警、工单安排、故障处理办法和作业合规性。
注：agent在生成答案过程中，必须以rag或者某种策略对数据库和文档进行检索，不得将整个数据库或者文档全部放入LLM的上下文中。

系统应能根据问题判断需要使用运行告警记录、维检工单记录、故障处理手册、检修作业与安全管理规程中的一种或多种资料。对于复杂问题，可以根据第一次查询结果继续查询其他数据表或文档，再基于获得的证据形成回答。

预计投入时间：半天至一天，约 6～8 小时。

你可以自由选择编程语言、AI 编程工具、Agent 框架、大模型和前端技术栈，包括但不限于 Codex、Claude Code、GitHub Copilot 等工具。

## 二、随题资料

候选人材料目录包含：

- `海上风电维检.db`：只读 SQLite 数据库，仅有 `alarm_records` 和 `maintenance_records` 两张业务表；
- `数据库说明.md`：表结构、字段和枚举值说明；
- `故障处理手册.md`：故障原理、触发条件、排查方法和注意事项；
- `海上风电机组检修作业与安全管理规程.md`：工单优先级、重复故障、远程复位、部件更换和工单关闭规则；
- `示例问题.md`：4 个不同层次的示例问题、解决思路和参考答案；
- `考察问题.md`：7 个用于展示应用场景的公开问题。

全部风场、机组型号、记录和制度均为虚构模拟数据，不代表任何真实企业或项目。

## 三、任务目标

自行搭建一个可运行的系统，让用户通过简单 Web UI 提问，并得到基于随题资料的回答。系统的重点是：

1. 理解问题并选择合适的数据源；
2. 安全、准确地查询数据库；
3. 从 Markdown 文档中定位相关章节或条款；
4. 在需要时进行多步查询和信息融合；
5. 区分“资料明确支持的事实”和“现有资料无法确认的事项”；
6. 向用户展示结论所依据的数据表、文档或章节。

## 四、建议能力与重点关注方向

以下内容用于说明重点方向，可按时间和方案取舍，不应理解为必须全部完成的硬性验收清单。

### 4.1 数据库查询

系统可以考虑做到：

- 理解两张表分别保存什么信息；
- 根据问题判断查询哪张表；
- 必要时依次查询两张表并关联 `turbine_id`、`fault_code`；
- 根据查询结果继续检索文档；
- 对 SQL 执行错误提供基本处理；
- 以只读方式访问数据库，避免修改题目数据。

### 4.2 文档检索

系统可以考虑做到：

- 检索两份 Markdown 文档；
- 按故障代码、故障名称或规程条款定位内容；
- 在回答中展示使用的文档和章节；
- 必要时同时使用两份文档，区分技术处理要求与管理规则。

### 4.3 多步查询

较复杂问题可能包含如下过程：

```text
理解问题
→ 判断需要查询的数据表或文档
→ 执行第一次查询
→ 根据结果决定是否补充查询
→ 融合数据库事实和文档规则
→ 生成回答并展示依据
```

可以采用 Function Calling、ReAct、状态机、固定工作流、自定义 Planner 或其他合理方案。不要求必须实现完全自主的通用 Agent。

### 4.4 UI 界面

系统应提供一个简单 Web UI。界面可包含（非强制要求）：

- 问题输入区域；
- 示例问题或能力说明；
- 查询中的状态反馈；
- 最终回答；
- 使用的数据表和文档来源；
- 简要查询过程；
- 错误或证据不足提示。

UI 主要关注信息是否清楚、用户是否知道系统能做什么、回答与依据是否容易区分、执行中是否有合理反馈，以及失败或证据不足时是否有明确提示。不要求复杂视觉设计，也不要求展示模型的完整内部思维过程。

## 五、数据与回答边界

- 数据库时间采用 `YYYY-MM-DD HH:MM:SS` 格式；题目中出现的时间范围均按闭区间理解，除非你的界面另有清楚说明。
- 对“最近一次状态”一类问题，应说明状态来自哪条最新告警记录。
- 需要判断工单安排时，应同时关注工单优先级、状态、处理记录、观察时间和备件字段，而不能只看是否存在工单。
- 当数据库或文档没有提供现场安全条件、责任调查结论等信息时，应明确说明证据不足，而不是补造事实。
- 不应执行写入、更新、删除或建表操作；数据库是只读题目资料。
